## Why (owner, 27 Oct)

Leadership (Mr Akbar, Ms Shadi, Dr Luvi) find reports.dentalnation.com confusing. The owner's requirements, in order:
1. **Every proof aligns.** A number in a daily email, on a tile, in a table and on its drill-down must be the SAME number for the same dates and clinic. No mismatch anywhere.
2. **Data aligns.** One definition per metric, computed by one function, reused everywhere.
3. **Easy to navigate and understand** for a non-technical CEO: he should answer his daily questions in one or two clicks, in plain words.
4. **See the new design before anything is built.**

## Known mismatches already found (verify each in code, then add any others you find)

1. **Billed revenue basis:** the performance email and `lib/performance/reader.ts` use `getChannelPerformance(..., { strict: true, excludeCancelledBills: true })`; the Growth page (`components/sections/growth/GrowthPlatform.tsx`) uses the defaults; Executive uses `getPractoSummary`; the Growth page shows attributed and unattributed revenue separately, rounded to 0.1k, while emails add them.
2. **Meta leads:** `lib/meta/detail.ts` `leadsFromActions` sums overlapping action types (one chat can count up to 4 times) while the briefing uses `lib/meta/people.ts` `metaPeople`; the Meta tab and the emails disagree.
3. **Three clinic vocabularies:** `clinic` (all|dental-nation|dr-tosun), `gclinic` (all|dn-alwasl|dr-tosun|amc), `bpclinic`/`gbpbranch` (all|dental-nation|dr-tosun|al-maher). Some sub-tabs ignore the clinic param (Practo appointments, `PractoReport.tsx`); Growth drill-down turns `amc` into all clinics.
4. **Enquiries by clinic do not exist:** enquiries are shared surfaces; Dr Tosun and Al Maher show empty or misleading splits.
5. **Al Maher has no patient-system feed** (no Practo), yet some views imply figures.
6. **Google Business Profile:** missing Google days are stored as 0 (`gmb-adapter.ts`), so "0 calls" can mean "not reported yet"; reviews card dates are UTC while emails use Dubai days; the GBP plan view (`otab=gbp`) cannot be date-pinned.
7. **Comparisons:** some views compare to the previous equal-length period, emails sometimes to "same days last month"; several deltas cannot be reproduced on any page.
8. **Practo doctor revenue:** priced bill lines usually have no conducting doctor, so per-doctor revenue is near zero; Revenue view shows top 7 + Other.
9. **Stale config:** `config/meta.ts` says Meta paused since April, but October has Meta spend.
10. **Smile Club panels** were not URL-addressable until 24 Oct (`?sc=team|scripts`); check every Smile Club figure has a proof view.
11. **Branded search share** uses only the top 250 Search Console queries; brand-search volume lives only inside the competitor view.

## Part A — Leadership usability audit (evidence)

1. Write the 10 questions leadership actually asks (from the emails and tabs: e.g. "How many enquiries yesterday and this month?", "How many booked and showed?", "What did we bill?", "What did ads cost per enquiry?", "Which clinic is behind?", "Is DN Ortho working?", "Is Smile Club growing?", "How are our Google reviews?"). For each: where it is answered today, number of clicks from login, the jargon on the way (e.g. "gross/net", "strict", "untraced desk pool"), and whether two places give two answers.
2. List every label, abbreviation and number format a CEO would not understand, with a plain-English replacement.
3. Run the app locally if you can (fixtures, no production data) and screenshot each start view at desktop and phone width; if it cannot run offline, say so and work from code.

## Part B — Metric registry (the core of "no mismatch")

Produce `out/metric-registry.md` (and a CSV): one row per leadership metric (enquiries, people, bookings, shows, no-shows, billed revenue, ad spend, cost per enquiry, cost per booking, GBP calls/directions/website clicks/map views, reviews count/average/new/unanswered, Smile Club members/bookings, DN Ortho enquiries/bookings/billing, brand searches, branded click share, Instagram followers/reach). Columns:
- plain-English name and one-sentence definition (what counts, what does not, which day boundary, which clinics)
- the ONE function that should compute it (existing or proposed), with exact options
- every place it is shown today (tab/sub-tab/email/export) with the function and options actually used there
- whether those places can disagree today, a concrete example of how, and the fix
- the proof view for it in the new design (URL) and a test that would guarantee the email figure equals that view

Then a short `out/consistency-plan.md`: how to make the registry enforceable in code (e.g. one `lib/metrics/` module that every page, export and email imports; a test that renders an email and the linked page from the same fixture and asserts equal numbers; date and clinic parameters parsed in one place with one clinic vocabulary and redirects from the old ones).

## Part C — New design (for the owner to see before anything is built)

1. Update DN-030's seven-section structure for what changed since (alerts, Smile Club deep links, DN Ortho campaign live since 23 Oct). Max 7 top-level sections, max one level of sub-tabs, each metric has ONE home, other places link to it.
2. A start view per person using the existing role model: Mr Akbar and Ms Shadi land on the leadership Overview; Dr Luvi on Clinics; marketing on Channels; reception keeps Clinical Operations.
3. HIGH-FIDELITY static HTML mockups (not ASCII), in the existing design system (read `tailwind.config.*` `dn` palette, existing components), self-contained files with inline CSS and sample figures clearly marked as samples, saved to `.agent-bus/outbox/DN-032-mockups/` with PNG screenshots:
   - `01-overview.html`: the CEO page: the five or six numbers that matter (yesterday and month to date), trend, clinic split where the data supports it, "what changed and why" in plain words, every number clickable to its proof.
   - `02-channels.html`: enquiries, bookings, spend and cost per enquiry by channel, with the drill-down.
   - `03-clinics.html`: per clinic, honest about Al Maher and shared enquiries.
   - `04-programmes.html`: DN Ortho and Smile Club.
   - `05-proof-drawer.html`: what a user sees when clicking any number: the definition, the source, the date range and clinic, last data refresh, and a link to the detail rows.
   - `06-navigation-mobile.html`: the navigation and Overview at phone width.
   Each mockup page must state, near each number, its registry metric id so reviewers can trace it.
4. A redirect map from every current URL (including every link pattern in `lib/alerts/links.ts` and DN-030's map) to its new home; nothing may 404 or silently show a different number.
5. Recommended answers to DN-030's 9 open decisions (one paragraph each, with the trade-off), so the owner can decide in one sitting.
6. A migration plan in small shippable, reversible steps, starting with the highest-value, lowest-risk one (likely: the metric registry module plus email-equals-page tests, with no visual change), each with effort, risk and what each user group notices.
