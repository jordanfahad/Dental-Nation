## Part B — WhatsApp lead alert for Dr Luvi (built, but OFF by default)

Decisions still with the owner (Fahad). Build the code so that nothing is
sent until these are set. Record in the handoff that they are open.

- Dr Luvi's current rule is shoot-schedule emails only. A lead alert is a
  new kind, `lead:whatsapp`. It must not appear in Smile Club lists.
- Email content must be counts only (standing rule). No names, phones,
  message text or row ids in the email. Link to the lead tracker sheet.

1. Config `config/lead-alerts.ts` exporting:
   - `LEAD_ALERT_MODE`: `'off' | 'batched' | 'instant'`, default `'off'`.
   - `LEAD_ALERT_RECIPIENT`: `null` (no recipient configured by default).
   - `LEAD_ALERT_BATCH_MINUTES`: `120`.
   - `LEAD_ALERT_WINDOW`: 09:00 to 21:00 Dubai.
   When mode is `off` or the recipient is `null`, the job writes one log
   line (`lead:whatsapp: not configured`) and sends nothing.
2. WhatsApp evidence is explicit only: a lead row counts when `whatsapp_ref`
   is non-empty, or `channel_source`, or the Inquiry Platform / Preferred
   Channel values in `raw_row`, contain "whatsapp" or "zavis". Do NOT use the
   default fallback of `leadTrackerChannel`. Pure function in
   `lib/lead-alerts/evidence.ts`, with tests.
3. New table via migration `supabase/migrations/0048_lead_alert_seen.sql`
   (additive only, not applied): `lane_e.lead_alert_seen (id text primary
   key, first_seen_at timestamptz not null default now(), alerted_at
   timestamptz)`. RLS enabled; revoke from public, anon, authenticated;
   grant to service_role only. Same pattern as 0047.
4. Seeding guard (critical): on the first run, when `lead_alert_seen` is
   empty, insert every current lead id with `alerted_at = now()` and send
   nothing. Otherwise the whole history would alert. Test this explicitly.
5. Each run after a sync: find lead ids not yet in `lead_alert_seen` that
   have WhatsApp evidence, insert them into `lead_alert_seen` with their
   `first_seen_at`, and count them for the next email.
   - `batched`: send at most one email per `LEAD_ALERT_BATCH_MINUTES`,
     only inside the window. Content: count of new WhatsApp leads since the
     last email, split by branch and by channel group, plus the link.
     Nothing is sent when the count is zero.
   - `instant`: one email per run that has new leads (not per lead), same
     count-only content. Still at most one per run.
   Mark `alerted_at` only after a successful send.
6. Send through the existing `sendEmail` transport, from `OPS_ALERT_FROM`,
   to the recipient only. Use the same claim-before-send pattern as
   `lib/performance/delivery.ts` so overlapping cron runs cannot double-send.
7. Add `lead:whatsapp` to Smile Club's exclusion list (the same
   `continue` pattern used for `am:*`) and add the kind to `ALERT_CAP` as
   "Dr Luvi: lead alert (off until configured)". Keep Dr Luvi's shoot-only
   Smile Club rule unchanged.
8. Freshness: alerts run after the lead sync, so a lead alert can lag the
   desk's entry by the sync interval (about 15 minutes) plus any delay in
   the desk logging it. State this in the email footer and in the handoff.
   Real instant alerts need a Zavis webhook or API. That is a separate task
   and is NOT part of this spec.
