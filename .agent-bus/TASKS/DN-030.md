# DN-030 — Dashboard redesign: audit the navigation and propose one clear structure
Mode: draft
Output: `.agent-bus/work/DN-030/out/redesign.md` plus screenshots (git-ignored), and the handoff `.agent-bus/outbox/DN-030.md` (committed; it carries the full proposal text, no patient data)

Run UNATTENDED, never stop to ask. This task PROPOSES; it changes no
product code. Hard rules: no production writes, no Supabase/MCP/SQL, no
email, no secrets, no patient data in anything committed (counts and labels
only). Public repo.

## Why (owner, 21 Oct)

The owner finds reports.dentalnation.com confusing: too many tabs and
sub-tabs, several showing the same numbers in different places, and no
obvious starting point. Mr Akbar, Ms Shadi, Dr Luvi and the clinic teams
all use it, and links to specific views are already in emails, so the
redesign must not break them.

## Part A — Audit what exists (evidence, not opinion)

1. Inventory every top-level tab (`components/tabs`, `app/(app)/page.tsx`)
   and every sub-tab query parameter (`mtab`, `gtab`, `gchan`, `btab`,
   `ptab`, `otab`, `dtab`, `mscope`, `mgrp`, `mchan`, `mcamp`, `gcamp`,
   `ccamp`, `comp`, `rdate`, `rcad`, `rcmp`, `mpipe`, `bpclinic`,
   `gbpbranch`, `gclinic` and any others) with: label, who can see it
   (role visibility in `effectiveVisibleTabs`), the main numbers it shows,
   and their data source function.
2. Find the duplicates: list every metric (enquiries, bookings, attended,
   billed revenue, spend, cost per enquiry, GBP calls, reviews, Smile Club
   members, etc.) and EVERY place it is shown. Flag where the same metric
   shows different numbers for the same range, and why (different source,
   different rule, different date logic).
3. Find dead ends: tabs with mostly empty or "unavailable" states, views
   nobody links to from emails (`lib/performance/emails.ts`, other email
   builders), and controls that do nothing.
4. Run the app locally if you can (`npm run dev` with mocked data or the
   existing fixtures) and take screenshots of each top-level tab; if the
   app cannot run offline, say so and work from the code.

## Part B — Propose the new structure

1. Group everything by the question the reader is asking, for example:
   **Overview** (one page for Mr Akbar: the five numbers that matter, with
   trend), **Demand** (enquiries by channel and source, gross vs actual),
   **Conversion** (enquiry to booking to attended to billed, by branch),
   **Channels** (paid search, Meta, GBP, website, partners: spend and
   results), **Clinics** (per-branch operations), **Programmes** (Smile
   Club, DN Ortho), **Admin** (users, data health). Improve on this if the
   audit suggests better groupings; justify each choice.
2. Maximum 7 top-level tabs and maximum one level of sub-tabs. Each metric
   has ONE home; other places link to it instead of re-computing it.
3. A role-based landing page: Mr Akbar lands on Overview, reception on
   their desk view, Marketing on Demand. Use the existing role model.
4. A wireframe for the Overview page and one for Demand (ASCII or simple
   HTML in the out folder).
5. A redirect map: every current `?tab=...&sub=...` URL to its new home, so
   links in sent emails keep working. Nothing may 404.
6. A migration plan in small, safe steps (each one shippable and
   reversible), with what changes for each user group and an estimate of
   effort per step. Step 1 should be the highest-value, lowest-risk change.

## Constraints

- Follow the existing design system and components; no new UI libraries.
- Do not remove any data or capability; only move, merge or hide.
- Numbers must not change meaning. Where two views disagree today, say
  which rule should win and why, as a decision for the owner.

(tab, sub-tab, audience, metrics, source), the duplicate-metrics table, the
proposed structure (tree), the redirect map, the migration steps, open
