Goal: Mr Akbar's daily brief (`am:akbar-perf`) and Ms Shadi's GBP daily
(`am:gbp-daily`) must not show numbers that contradict each other. Two
problems were found while previewing the emails on synthetic data.

Problem 1: gross and net land in different channel groups for the same
leads. Gross (raw tracker rows) is classified by `parseGrossRows` in
`lib/performance/core.ts`, which calls `leadTrackerChannel` in
`lib/growth/attribution.ts`. That function ends with
`return 'whatsapp'` as a default, so any tracker row that matches no
explicit rule is grouped as Organic digital. Example from the preview: a
row with Source Type "Paid" and Inquiry Platform "Google" matches no
paid rule, becomes Organic digital, and the table shows Organic gross 65
while Paid digital net is 41 for the same day. Net comes from Growth's
channel report, which does classify that traffic as paid.

Problem 2: billed patients do not reconcile with the new/existing split.
The "Billed patients" column in the funnel comes from Growth's treated
count (`summarise` in `buildPeriod`). The New / Existing / Unclassified
columns come from the billing files (`patientSplits`). Nothing checks
that they agree, so the email can show "billed 8" next to "new 0,
existing 0, unclassified 0".

## What to build

1. Add a NEW pure function in `lib/performance/core.ts` (for example
   `performanceChannel(sourceType, inquiryPlatform, preferredChannel,
   notes)`) that reuses the same tag and tracker rules as
   `leadTrackerChannel` and `tagHit`, but returns `null` when no explicit
   rule matches, instead of the `whatsapp` default. Do NOT change
   `leadTrackerChannel`, `tagHit` or any existing export: the Growth
   dashboard and Smile Club depend on them, and their numbers must not move.
2. `parseGrossRows` uses the new function. A `null` result becomes a new
   group `Unclassified` (add it to `GROUPS`, placed after Existing
   patients; add a matching entry to `groupOf` only through the parser,
   never by guessing a channel). Rows with a real explicit rule keep their
   current group. Do not add a rule for a label you have not seen in a
   real tracker value. If you can see the real tracker export locally under
   `.agent-bus/work/`, you may report counts of distinct Source Type and
   Inquiry Platform labels in the handoff (labels and counts only, zero
   rows, zero names). Do not add a new rule from that list without
   recording the label and the reason in the handoff.
3. The funnel table in `buildPeriod` keeps the Growth billed count, but
   the email must make the relationship explicit. Rename the columns so
   the source is visible: "Billed patients (Growth)" in the funnel and
   "Patients by billing file" in the patient table. When the billing-file
   count for a clinic is not equal to the Growth billed count for that
   clinic over the same window, add a data note to that clinic's row:
   "Billing-file count differs from Growth billed count by N; the funnel
   shows the Growth count." Where the billing file feed is absent for a
   clinic, keep the existing "Unavailable" wording and do not compare.
4. Gross and net are different populations. In `DEMAND_NOTE` (or next to
   the funnel table) state once that group-level gross and net are not
   directly comparable because classification sources differ. Keep the
   sentence short and plain, hyphens only, no em dashes.
5. Growth numbers, the Smile Club alerts, `alertRules.ts`, the claims
   table code path, `lib/performance/delivery.ts` caps and the cron
   entry must not change. The GBP "Off track" status rule must not change
   either (that decision is still open with the owner).
