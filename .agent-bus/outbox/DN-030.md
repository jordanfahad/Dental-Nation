# DN-030: One reporting dashboard, seven clear starting points

Proposal only, audited on 21 October 2026 against `516ecfc5aa3ef1906b6dc55c899ddbebe06f512e`. Product code is unchanged. No live data was read, and no database, SQL or MCP calls or email sends were made. Work stayed on main. Only this handoff is intended for commit. The full proposal is also delivered in `.agent-bus/work/DN-030/out/redesign.md`, with two text wireframes. Live preview and screenshots were skipped for this final code-based handoff, as requested. Implementation and metric-policy choices below remain proposals for the owner.

The main problem is overlapping jobs, not simply too many labels. There are **20 reporting tabs**, plus the separate application navigation. Executive embeds Growth Platform; Group Revenue also houses Growth Platform, KPI Benchmarks and Marketing OS. Head of Operations has 11 views covering finance, marketing, clinics, programmes and a procurement placeholder. There is no single date or counting contract across these surfaces.

Recommend **Overview, Demand, Conversion, Channels, Clinics, Programmes, Admin**. Each metric gets one owning page and one definition. Overview displays five linked summaries from those owners. Reports and emails consume the same values; specialist pages link to other metric homes rather than creating another funnel.

`effectiveVisibleTabs` takes the base list, adds known `extra_tabs` except Users/Status, then subtracts `removed_tabs`. Admin always keeps all 20. Thus any S, O, G or A+ view can be individually granted or removed. The six base-role counts are admin 20, viewer 14, staff 13, clinician 15, opsstaff 14, receptionist 1. Sub-tabs inherit the parent grant; they do not each have their own visibility rule. Page-specific edit checks still apply.

An important exception to reasoning from tab names: Executive already embeds the full Growth summary for S users, even when they cannot open Group. Preserve that existing summary visibility when consolidating; it does not automatically grant the Group-only patient trace.

Default is Executive for every role except receptionist, who defaults to Clinical Operations. An unavailable requested tab falls back to the role default or first visible tab. A known denied tab produces a notice. There is no Marketing role, no stored branch restriction in this role model and no named-user landing preference today. Names in comments are intent, not evidence of current account grants. No user directory was queried.

## Proposed structure

There are seven top-level tabs and one level of sub-tabs. Everything after a sub-tab below is an in-page section, an anchor, a filter on a data dimension, or an action. There are no tertiary tab bars.

```text
Overview
  Summary             Five linked metrics, trends, coverage and action links
  Reports             Daily / weekly / board / CEO format selector, print/export

Demand
  Enquiries           Gross tracker rows, net people, source and branch evidence
  Treatment themes    Existing Demand to desk, market and creative learning
  Reconciliation      Platform, GA4 and tracker populations side by side

Conversion
  Funnel              Period enquiries -> appointments -> attendance -> billed
  Patient journey     Existing CRM cohort journey, follow-up and paid state
  Patient value       First-bill acquisition, cost, observed cohort value
  Retention           Returning files, cohort returns and reactivation evidence

Channels
  All channels        Link directory; no second set of channel totals
  Paid media          Google / Meta filter, campaigns, costs and diagnostics
  Local & social      GBP results + plan, reviews, organic social, benchmarks
  Website & SEO       GA4, booking events, GSC, SEO, speed, competitors, Clarity
  Partners            Affiliates, influencers, referral partnerships; Araby detail

Clinics
  Desk                Verified / campaign / unverified worklists, call actions, CRM
  Appointments        Practo diary analytics, manual daily report as dated evidence
  Finance             Finance production, operating billing link, cash, history,
                      Procurement connection state; no mixing money bases
  Doctors             Provider production, capacity and dated commission controls
  Operations report   Existing editable narrative and evidence sections

  Smile Club          Outcomes, plan, all 14 panel contents as anchored sections
  DN Ortho            Campaign, consultation and follow-up evidence
  Content calendar    Cross-programme calendar; campaign is a filter
  Delivery            Growth Projects, Marketing OS pipelines, approvals, risks,
                      KPI definitions/benchmarks and effort register

  Data health         Coverage, sync, incidents, rules, measurement gaps
  File handover       Existing Data Drop capability with existing access checks
  Users               Existing admin-only directory and grants
```

Why these boundaries: Demand answers who contacted us and how they were counted. Conversion answers what happened at the clinic. Channels answers where to improve distribution and spending. Clinics is where teams act, while Programmes holds bounded initiatives and delivery work. Overview has a five-number summary, not a second copy of every report. Admin contains source/account maintenance. Keeping Conversion separate from Clinics prevents operational worklists from becoming the group's financial scorecard.

**One home means one definition and one owning detail page.** Overview may render a compact, linked projection of the owner's already-computed result. Reports/emails are presentations of the same result and definition version. They may not run independent aggregation rules. Channels links to filtered Demand/Conversion results; Clinics links to official outcome totals. Shared components are acceptable; parallel readers and unlabeled copies are not.

Each result should carry metric ID, unit, population, date field, branch scope, source coverage/as-of, method (measured/inferred/modelled/manual), null reason and definition version. This can begin as TypeScript objects and existing components, with no new UI library or storage requirement. Resolve the range once; pass it and scope to the owner. Do not force an undated manual snapshot into that range.
