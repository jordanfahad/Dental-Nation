## Behaviour and decisions made for this task

Reception counts are gross normalized rows from `lane_e.leads` whose `source_sheet` is the configured Inhouse Lead Tracker label. They are not deduplicated people and need not equal the separate raw-sheet funnel population. The same five groups plus DN-016's Unclassified bucket are displayed, including zeroes. Unknown evidence is Unclassified, never default Organic digital. Booked uses the existing Growth Platforms statuses: booked, confirmed, attended and completed, with its existing trim/case handling. No new booking statuses were invented.

Yesterday and MTD end on the previous Dubai day. On the first of a month, MTD is the completed month containing yesterday, matching the existing brief. No-source is per window. Future-dated is a tracker-wide count of dates after yesterday, including today; those rows are excluded from the completed-period counts but explicitly counted. Last sync is the maximum lead-row timestamp across the tracker, displayed in Dubai time. Both tracker-wide diagnostics repeat in the two table rows.

The task's known July 2027 stray row was not inspected live, corrected or deleted. The implementation counts it if it is present. The synthetic output below has two rows after yesterday: one dated today and one in July 2027. These are fixture results, not claims about current business data.

The WhatsApp evidence gate accepts any nonempty `whatsapp_ref`, or WhatsApp/Zavis text in `channel_source`, raw Inquiry Platform or raw Preferred Channel. Source Type and notes alone do not qualify. There is no default-channel fallback. Classification for the email's group split reuses the same explicit gross classifier. Branches use the existing canonical branch mapper; unknown text becomes the fixed Unassigned label and is never echoed.

Both delivery modes use 09:00 inclusive to 21:00 exclusive Dubai. Discovery runs outside delivery hours once configured, so pending rows carry into the next window. Instant means one count-only email per eligible sync run. Batched sends the first eligible pending batch, then enforces a rolling interval from the latest delivery claim or successful-send timestamp. Zero pending rows send nothing. Discovery inserts ignore existing rows, preserving the original first-seen and alerted timestamps.

An atomic advisory-lock-protected claim is persisted before sending. Claimed rows cannot be claimed again, including after a failed/uncertain transport or a successful send whose marking step failed. `alerted_at` is set only after a successful send, except for the explicitly required history seed. Held claims therefore require operator review if recovery is needed; the job never automatically retries them. This follows the existing performance-delivery preference for avoiding duplicate email. The claim RPC returns one scalar array so a large batch cannot be silently truncated by the API's row-response limit. A 1,001-row synthetic burst is covered.

The new path also respects the existing `alerts_paused` owner switch and fails closed on a pause-read failure or unavailable email transport. All its log lines are fixed messages or counts. Raw upstream errors and lead fields are not logged. Transport receives only the configured recipient, with no cc or inherited operations recipients, and uses `OPS_ALERT_FROM` through the existing `sendEmail` wrapper.

## Migration apply note for Claude

Review and apply `supabase/migrations/0048_lead_alert_seen.sql` once to the intended database before enabling the lead alert. It creates `lane_e.lead_alert_seen`, the supporting `lane_e.lead_alert_claims` table and three security-invoker functions. The extra claim table is necessary because the existing performance claims are restricted to the two daily performance kinds, and the lead alert needs a rolling interval and durable per-lead claims. Both new tables have RLS enabled; public, anon and authenticated have all privileges revoked; only service_role receives table/function access. No existing table, recipient or performance claim is altered.

The seeding guard runs automatically on the first eligible sync after the table exists: once mode/recipient/transport are configured and the owner pause is clear, an empty seen table is populated with every current lead, with `alerted_at = now()`, and that run sends nothing. While mode is off or recipient is null, the hook deliberately only writes `lead:whatsapp: not configured` and makes no database calls. Thus applying the migration alone does not activate or seed the job. If the source has no rows, it stays conservative and seeds the first populated snapshot without sending. Later runs discover only unseen WhatsApp-evidenced rows. No manual historical seed is needed.
