## Exact writer and reader rules

The supplied DN-023 schema evidence says `lane_e.social_insights.value` is numeric NOT NULL and the primary key is `(clinic, channel, metric, day)`. The implementation uses that evidence without querying production or changing the schema.

For each valid observation, the writer upserts `review_count`, including a real zero. It includes a `rating` row only when the count is positive and the rating is finite and between 1 and 5. Every upsert value is numeric. The channel stays `benchmark`; the conflict key stays `clinic,channel,metric,day`; weighted averaging, rounding, Dubai dates and active Al Wasl location scoping remain intact. Empty/failed competitor listings and incomplete review counters still create no observation.

When a rating is unavailable, the writer first deletes only the matching clinic/channel/metric/day rating row, then upserts the count. This handles a valid-to-unavailable retry on the same day without submitting a null or leaving stale stars. Earlier days and other clinics remain untouched. If that targeted deletion fails, the clinic is recorded as failed and its count is not advanced; processing continues for the other clinics. All of this remains inside the existing weekly cache-miss path. No live delete or upsert was executed during this task.

For each benchmark profile, the latest stored review-count row up to `asOf` establishes the observation day. The reader shows a rating only from that same case-normalized profile and day, with a valid 1-to-5 value and positive review count. An older rating, a rating-only row, or a missing same-day rating cannot supply stars for the observation. The own-profile GBP fallback fills count and rating together only when no stored own review-count observation exists up to `asOf`; it never fills a missing metric once a stored count exists.

Count deltas still require two stored values exactly 30 days apart on the same profile. Rating deltas require valid rating values on those exact endpoints; either missing endpoint yields null. Instagram follower selection and delta behavior are unchanged. The email renderer is unchanged and already renders an unavailable rating as `no public signal stored`.

Comparison availability is assessed independently for tracker leads, booking source rows and billing source rows across all branches from the previous month's first day through yesterday. Valid dated tracker rows establish tracker presence. Dated billing rows establish billing presence even when all invoices are cancelled, but cancelled invoices never add revenue. Booking presence uses a date-filtered `practo_appointments_raw` read with `limit(1)`, because Growth's existing `apptFeedRows` counts all history. The presence read fails closed on an error.

If a source has no rows in that combined window, its metric is null for every branch in both periods and the table names the source. If it has rows anywhere in the window, a branch/period with no events shows a real zero. Al Maher bookings and revenue remain null regardless. Missing tracker data also makes the unassigned-lead footnote Unavailable. Out-of-window history does not establish coverage. Existing GBP partial-day coverage, calendar windows, canonical tracker branch mapping and recorded outcomes are preserved.
